# Device ID Migration Architecture

This document describes how **Volume Locker** reliably tracks audio devices and migrates user configurations (volume locks, unmute locks, and priority lists) when Windows changes their endpoint IDs.

For the related migration of Windows-assigned custom endpoint names and logo URIs, see [Windows Audio Endpoint Property Migration](./device-property-migration.md).

---

## The Problem

Windows Core Audio (WASAPI) identifies audio endpoints using ephemeral GUIDs:

- Output: `{0.0.0.00000000}.{GUID}`
- Input: `{0.0.1.00000000}.{GUID}`

These GUIDs are frequently regenerated by the Windows `AudioEndpointBuilder` service:

```mermaid
flowchart LR
    A[Physical Audio Device] -->|Move to another USB port| B[New Endpoint GUID]
    A -->|Unpair & re-pair Bluetooth| B
    A -->|Driver or Windows Update| B
    A -->|Windows resets friendly name| B
    B -->|Without Migration| C[❌ Lost volume locks & priority order]
    B -->|With Volume Locker| D[✅ Settings seamlessly transferred]
```

## Architectural Overview

Volume Locker handles device ID changes via three components:

```mermaid
graph TB
    subgraph Detection["1. Event Triggers"]
        IMM[IMMNotificationClient<br/>Device Added / Removed / State / Prop Change]
        PWR[RegisterSuspendResumeNotification<br/>System Wake / Resume]
    end

    subgraph Recovery["2. Metadata & Fingerprint Recovery"]
        STORE[Windows COM Property Store<br/>GetDevice on disconnected endpoint]
        CACHE[Saved DeviceFingerprint<br/>Config fallback]
    end

    subgraph Matching["3. 6-Tier Migration Cascade"]
        T1[Tier 1: Hardware ID - MAC / Serial]
        T2[Tier 2: USB Profile - VID/PID + Interface]
        T3[Tier 3: Internal Audio Profile]
        T4[Tier 4: Custom Name Match]
        T5[Tier 5: Normalized Original Name]
        T6[Tier 6: Fallback VID/PID]
    end

    Detection --> Recovery
    Recovery --> Matching
    Matching -->|Match Found| APPLIED[Migrate Settings & Notify User]
    Matching -->|Ambiguity / Collision| REJECT[Safely Reject - No guessing]
```

## 1. On-The-Fly Property Store Recovery & In-Memory Fingerprint Cache

When a USB device is unplugged or re-enumerated, Windows transitions the old endpoint to `DEVICE_STATE_NOTPRESENT` (`4`). While activating audio streams fails, **Windows preserves the complete COM property store in the registry**:

However, when a Bluetooth device is **unpaired** in Windows Settings, Windows completely uninstalls and deletes the endpoint (`0x80070490 Element not found`). To protect unpairing and re-pairing workflows, Volume Locker maintains an in-memory `device_cache` of all active endpoints:

```mermaid
sequenceDiagram
    autonumber
    participant APP as Volume Locker
    participant MM as Windows MMDevice API
    participant MEM as In-Memory Device Cache
    participant REG as Windows Registry (MMDevices)
    participant CFG as PersistentState (Config)

    alt Disconnected USB endpoint (DEVICE_STATE_NOTPRESENT)
        APP->>MM: IMMDeviceEnumerator::GetDevice(old_id)
        MM->>REG: OpenPropertyStore(STGM_READ)
        REG-->>APP: Return PKEY properties (Hardware ID, Names, FormFactor)
        Note over APP: Fingerprint recovered on the fly!
    else Unpaired Bluetooth endpoint (Element not found)
        APP->>MEM: Query in-memory device cache
        MEM-->>APP: Return cached fingerprint (Bluetooth MAC address)
        Note over APP: Fingerprint recovered from memory cache!
    else Offline fallback (Cold start / App restart)
        APP->>CFG: Read saved fingerprint from config
        CFG-->>APP: Return persistent fingerprint fallback
    end
```

Because of this tiered recovery, Volume Locker seamlessly migrates settings even across complete Bluetooth unpairing and USB port changes.

## 2. Hardware Fingerprints

The `DeviceFingerprint` captures immutable hardware descriptors extracted from the endpoint's `IPropertyStore`:

```mermaid
classDiagram
    class DeviceFingerprint {
        +DeviceBusType bus_type
        +String hardware_desc
        +String interface_name
        +String clean_original_name
        +bool is_custom_name
        +String mac_address
        +Option~(u16, u16)~ usb_vid_pid
        +String usb_serial
        +u8 interface_index
        +String container_id
        +u32 form_factor
    }
```

- **Bluetooth (`BTHENUM`)**: 48-bit MAC address (`BD_ADDR`) extracted from the PnP interface string. Persists across unpairing and re-pairing.
- **USB (`USB`)**: Vendor ID, Product ID, sub-interface index (`MI_xx`), and serial number (distinguished from synthetic port topology hashes).
- **Display / Motherboard (`HDAUDIO`, `PCI`)**: Driver subsystem ID, monitor description, and form factor.
- **Form Factor (`PKEY_AudioEndpoint_FormFactor`)**: Prevents cross-migrating between different profiles (e.g. A2DP Stereo Headphones vs. HFP Hands-Free Headset, or Game vs. Chat audio channels).

## 3. Name Normalization & Anti-Cross-Matching

Windows derives the default friendly name from two driver properties:
$$\text{Friendly Name} = \text{DeviceDesc} + \text{" ("} + \text{DeviceInterface\_FriendlyName} + \text{")"}$$

> Note: registry inspection shows the name edited in Sound Settings is stored in `PKEY_Device_DeviceDesc` itself, so the comparison below cannot reliably detect a rename. `is_custom_name` is only a matching heuristic; property restoration ([Windows Audio Endpoint Property Migration](./device-property-migration.md)) does not depend on it.

When a user customizes a device name in Windows Sound Settings, the friendly name no longer follows the default template:

```mermaid
flowchart TD
    subgraph Inspection[Custom Name Detection]
        FN[PKEY_Device_FriendlyName]
        DD[PKEY_Device_DeviceDesc]
        IF[PKEY_DeviceInterface_FriendlyName]
        COMP{FriendlyName == DeviceDesc + ' (' + InterfaceName + ')'?}
        FN & DD & IF --> COMP
        COMP -->|No| CUSTOM[is_custom_name = true]
        COMP -->|Yes| DEFAULT[is_custom_name = false]
    end
```

### Safety Rules

1. **Anti-Cross-Matching**: Never match a custom friendly name against a driver's default name.
   - _Prevents:_ A custom-named `"Speakers"` endpoint incorrectly matching a newly plugged `"Speakers (USB Audio Device)"`.
2. **Normalized Original Matching**: Windows PnP injects port prefixes (e.g. `"2- "`) and clone counters (e.g. `" (1)"`) into `DeviceInterface_FriendlyName` when devices are moved across USB ports. Normalization strips these before matching:

```mermaid
flowchart LR
    RAW["2- Logitech USB Headset (1)"] -->|Strip '^\d+\s*-\s*'| S1["Logitech USB Headset (1)"]
    S1 -->|Strip '\s*\(\d+\)$'| CLEAN["Logitech USB Headset"]
```

3. **Bus-Type & VID/PID Isolation**: Endpoints with differing hardware buses (e.g. motherboard `HDAUDIO` vs. `USB` or `Bluetooth`) or conflicting USB VID/PIDs are strictly prevented from matching across all tiers.
   - _Prevents:_ Motherboard speakers named `"Speakers"` from cross-migrating onto a newly attached USB or Bluetooth speaker.
4. **Active In-Use Protection**: Active endpoints that are already participating in priority lists or active temporary priority overrides are excluded from the candidate pool.
   - _Prevents:_ Currently assigned or active priority devices from being claimed or overwritten as migration targets.

## 4. The 6-Tier Migration Cascade

Volume Locker compares **missing registered devices** against **unclaimed active devices** through six prioritized confidence tiers:

```mermaid
flowchart TD
    START([Unclaimed Active & Missing Devices]) --> T1

    T1{"Tier 1: Exact Hardware ID<br/>• Bluetooth MAC OR USB Serial<br/>• DeviceType & FormFactor match"}
    T1 -->|Match| MIGRATE[Migrate Device ID]
    T1 -->|No Match| T2

    T2{"Tier 2: USB Profile<br/>• USB VID/PID + MI_xx + Desc + FormFactor<br/>• Unambiguous 1:1 match"}
    T2 -->|Match| MIGRATE
    T2 -->|No Match| T3

    T3{"Tier 3: Internal Audio Profile<br/>• HDAUDIO Subsystem + Desc + FormFactor"}
    T3 -->|Match| MIGRATE
    T3 -->|No Match| T4

    T4{"Tier 4: Custom Name Match<br/>• Both devices have is_custom_name = true<br/>• friendly_name == friendly_name<br/>• DeviceType match"}
    T4 -->|Match| MIGRATE
    T4 -->|No Match| T5

    T5{"Tier 5: Normalized Original Name<br/>• clean_original == clean_original<br/>• BusType + FormFactor + DeviceType<br/>• Unambiguous 1:1 match"}
    T5 -->|Match| MIGRATE
    T5 -->|No Match| T6

    T6{"Tier 6: Heuristic Fallback<br/>• Unclaimed VID/PID or clean name<br/>• BusType + FormFactor compatibility<br/>• Strictly 1 missing to 1 active pair"}
    T6 -->|Match| MIGRATE
    T6 -->|No Match| NONE([No Migration / Safe Abort])
```

### Collision Rejection

For non-serial USB devices or shared original names (e.g. two identical microphones or generic audio dongles), Volume Locker **never guesses**. If multiple missing or active candidates qualify for Tiers 2, 5, or 6, migration is rejected to prevent swapping settings between identical peripherals. Furthermore, active devices currently assigned to priority lists or active temporary priorities are protected from being treated as unclaimed candidates.

## 5. Event Triggers & Power Resume Architecture

Device ID migrations and volume locks are completely event-driven with zero periodic polling:

```mermaid
flowchart LR
    subgraph Sources[Event Sources]
        WIN_NOTIF[IMMNotificationClient<br/>• OnDeviceAdded<br/>• OnDeviceRemoved<br/>• OnDeviceStateChanged<br/>• OnDefaultDeviceChanged<br/>• OnPropertyValueChanged]
        WIN_PWR[RegisterSuspendResumeNotification<br/>• PBT_APMRESUMEAUTOMATIC<br/>• PBT_APMRESUMESUSPEND]
    end

    subgraph AppLoop[Volume Locker Event Loop]
        EVENT[UserEvent::DevicesChanged]
        MIG[migrate_device_ids_if_needed]
        LOCK[Synchronously enforce volume/unmute locks]
    end

    WIN_NOTIF -->|Immediate callback| EVENT
    WIN_PWR -->|Wake from sleep| EVENT
    EVENT --> MIG
    MIG --> LOCK
```

- **`OnPropertyValueChanged`**: Filtered strictly to `PKEY_Device_DeviceDesc` (what Sound Settings edits on rename), `PKEY_Device_FriendlyName` and `PKEY_AudioEndpointLogo_IconPath`, so it only fires when a user renames an endpoint or changes its icon. Device info refreshes persist state when a tracked device's name or fingerprint changed, ignoring continuous driver telemetry (volume, battery, routing, peak meters).
- **Atomic Event Coalescing**: Rapid bursts of hardware events (e.g. `OnDeviceAdded`, `OnDeviceStateChanged`, `OnDefaultDeviceChanged`) during peripheral connection are coalesced into a single event loop dispatch.
- **Rich Event Attribution**: Windows callbacks capture the affected `DeviceId` and state transition for the event loop, providing clear and contextual diagnostic logging without blocking COM threads.
- **Power Resume**: Handles modern standby and system sleep wakeups, synchronously clamping volume levels in case Windows audio drivers reset endpoint volumes on wake.
