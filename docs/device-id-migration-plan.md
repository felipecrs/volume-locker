# Robust Audio Device Identification & Migration Plan

This document details the architectural design and implementation plan for improving audio device identification and ID migration in **Volume Locker**, addressing GitHub Issue [#85](https://github.com/felipecrs/volume-locker/issues/85).

---

## 1. Executive Summary & Problem Statement

### The Problem
Windows Core Audio (WASAPI / MMDevice API) assigns audio endpoint identifiers of the format:
```text
{0.0.0.00000000}.{GUID} (Render / Output)
{0.0.1.00000000}.{GUID} (Capture / Input)
```
These GUIDs are ephemeral and frequently regenerated by the Windows `AudioEndpointBuilder` service under routine circumstances:
- **USB port changes**: Plugging a USB headset, DAC, or microphone into a different USB port causes Windows to generate a new endpoint GUID unless the hardware provides a globally unique serial number (most consumer devices do not).
- **Bluetooth re-pairing**: Unpairing and re-pairing a Bluetooth audio device creates a completely new endpoint GUID even though the physical hardware and MAC address remain identical.
- **Driver updates & OS upgrades**: GPU driver updates (NVIDIA, AMD) regenerate HDMI/DisplayPort audio endpoint GUIDs; motherboard audio updates (Realtek, Intel) regenerate analog output GUIDs.
- **Custom renaming**: When users rename devices in Windows Sound Settings, Windows persists the custom string in `PKEY_Device_FriendlyName`. However, on re-enumeration or driver updates, Windows frequently resets the name to the driver default (e.g. `USB Audio Device` or `2- Logitech USB Headset`), breaking name-based matching.

### The Objective
Volume Locker must reliably match newly arrived or re-enumerated audio endpoints to previously saved configurations without losing volume lock policies, unmute lock policies, or device priority positions.

## 2. Windows Core Audio Internals & Discoveries

### Discovery: Retained Property Stores of Disconnected Devices
When a device is unplugged or disconnected:
1. Windows transitions the endpoint's state from `DEVICE_STATE_ACTIVE` (`1`) to `DEVICE_STATE_NOTPRESENT` (`4`) or `DEVICE_STATE_UNPLUGGED` (`8`).
2. Activating the audio volume interface (`device.Activate(IAudioEndpointVolume)`) fails with `0x80070003` (`ERROR_PATH_NOT_FOUND`).
3. **Crucially, `IMMDeviceEnumerator::GetDevice(old_device_id)` and `device.OpenPropertyStore(STGM_READ)` continue to succeed.** Windows retains the complete hardware property store in the registry (`HKLM\...\MMDevices\Audio\Render|Capture\{GUID}\Properties`) for disconnected devices.

### Architectural Advantage
Volume Locker **does not require users to have saved fingerprints prior to an upgrade**. When Volume Locker encounters an unrecognized or missing `old_device_id`, it can query `GetDevice(old_device_id)` to recover the disconnected device's exact hardware descriptor, PnP interface path, USB VID/PID, and Bluetooth MAC address on the fly. A persistent fingerprint stored in `DeviceSettings` serves as a secondary offline backup if Windows ever purges its registry cache.

## 3. Hardware Fingerprinting by Device Category

All necessary hardware metadata is exposed directly through the COM `IPropertyStore` of the `IMMDevice`:

### A. Bluetooth Audio (`BTHENUM`, `BTHLEENUM`, `BTHHFENUM`)
- **Bluetooth MAC Address (BD_ADDR)**: 48-bit physical hardware address (12-character hex). Immune to unpairing, re-pairing, or renaming.
  - Source: Parsed from the PnP Interface string (`{b3f8fa53-0004-438e-9003-51a46e139bfc}, 2`):
    ```text
    {1}.BTHENUM\{0000110B-...}_VID&00010075_PID&A013\A&1AF4467A&0&A0AC69494DD3_C00000000
                                                                   ^^^^^^^^^^^^ (MAC)
    ```
- **Profile / FormFactor**:
  - `A2DP` (Stereo headphones playback): `PKEY_AudioEndpoint_FormFactor = 3` (Headphones)
  - `HFP/HSP` (Hands-Free mono communication + mic): `PKEY_AudioEndpoint_FormFactor = 5` (Headset)

### B. USB Audio (`USB`)
- **VID (Vendor ID) & PID (Product ID)**: 16-bit identifiers (e.g., `VID_046D&PID_0A66`).
- **Mutual Interface Index (`MI_xx`)**: Distinguishes independent sub-interfaces on composite devices (e.g. `MI_00` for Game channel, `MI_01` for Chat channel, `MI_02` for Microphone).
- **USB Serial Number**:
  - If present: Instance ID format is `USB\VID_xxxx&PID_yyyy\<SERIAL>`.
  - If absent: Instance ID contains ampersands representing port topology (e.g., `USB\VID_xxxx&PID_yyyy\8&11e19ead&0&0000`).
- **Container ID (`PKEY_Device_ContainerId`)**: Windows assigns a physical container GUID. Modern USB audio devices implementing Microsoft OS 2.0 descriptors report persistent container GUIDs across all USB ports.

### C. Display & Motherboard Audio (`HDAUDIO`, `PCI`)
- **GPU DisplayPort / HDMI Audio**:
  - Hardware ID: `HDAUDIO\FUNC_01&VEN_10DE&DEV_009D&SUBSYS_10DE163F...`
  - Monitor Name: Stored in `PKEY_Device_DeviceDesc` (e.g., `LU28R55`).
  - Matching combination: `VEN/DEV/SUBSYS` + Monitor `DeviceDesc` + `FormFactor`.
- **Motherboard Audio (Realtek, Intel)**:
  - Hardware ID: Subsystem identifier `SUBSYS_18492897` specifies motherboard model.
  - Matching combination: Subsystem ID + `FormFactor` (Speakers vs Headphones vs SPDIF).

### D. Virtual Audio Devices (`ROOT`, `SWD`)
- Software drivers (VoiceMeeter, Elgato Wave Link, SteelSeries Sonar, NVIDIA Broadcast) have enumerator `ROOT` or `SWD` and specific driver hardware IDs (e.g., `root\fifineVirtualAudioDriver`, `root\LogiMIXLINE`).
- Matching combination: Enumerator + Driver Hardware ID + `DeviceDesc`.

## 4. Critical Edge Cases & Protection Mechanisms

### 1. Multi-Endpoint Disambiguation (Game vs Chat & Stereo vs Hands-Free)
Many headsets expose multiple endpoints sharing identical MAC addresses or USB VID/PIDs:
- **Bluetooth**: Samsung Galaxy Buds, Sony WH-1000XM, AirPods expose both *Headphones (Stereo)* and *Headset (Hands-Free AG Audio)*.
- **USB Gaming Headsets**: SteelSeries Arctis, Astro A50, HyperX Cloud expose both *Game Audio* and *Chat Audio*.

**Rule:** Migration candidate matching must strictly enforce:
1. `DeviceType` matching (`Input` to `Input`, `Output` to `Output`).
2. `PKEY_AudioEndpoint_FormFactor` matching.
3. Interface index / profile matching (`MI_00` to `MI_00`, `MI_01` to `MI_01`).
*Never migrate across different form factors or interface indices.*

### 2. User-Renamed Devices vs Windows Name Resets: Anti-Cross-Matching & Normalization

#### How Windows Generates Audio Names
Windows endpoints store three distinct name properties in the COM property store:
- `PKEY_Device_DeviceDesc` (`{a45c254e-...}, 2`): Endpoint category/role (e.g. `"Speakers"`, `"Headphones"`, `"LU28R55"`, `"Logitech G533"`).
- `PKEY_DeviceInterface_FriendlyName` (`{026e516e-...}, 2`): Underlying audio adapter or product (e.g. `"Realtek(R) Audio"`, `"Buds2 Pro de Felipe"`, `"2- Logitech Webcam C930e"`).
- `PKEY_Device_FriendlyName` (`{a45c254e-...}, 14`): The user-facing display name.

By default, Windows synthesizes `PKEY_Device_FriendlyName` via this template:
$$\text{Default Friendly Name} = \text{DeviceDesc} + \text{ " (" } + \text{DeviceInterface\_FriendlyName} + \text{")"}$$

When a user customizes a device name in Windows Sound Settings (e.g. renaming `"Speakers (Realtek(R) Audio)"` to `"Studio Monitors"`):
- Windows overrides **only** `PKEY_Device_FriendlyName`.
- `DeviceDesc` and `DeviceInterface_FriendlyName` remain **immutable**.

This allows deterministic detection of custom user naming:
```rust
let is_custom_name = friendly_name != format!("{device_desc} ({interface_name})");
```

#### Rule A: The Anti-Cross-Matching Principle
**Never compare a Custom Friendly Name against an Original Device Name.**
- *The Hazard:* If a user custom-renames an internal motherboard headphone jack to `"Speakers"`, and later plugs in a new USB soundbar whose original default name is `"Speakers (USB Audio Device)"`, a cross-category match would evaluate `"Speakers" == "Speakers"`. Volume Locker would mistakenly migrate the internal headphone settings onto the USB soundbar!
- *The Invariant:* Custom names must only match custom names. Original names must only match original names.

#### Rule B: Custom-to-Custom Matching
- When **both** the stored device and candidate active device have `is_custom_name == true`:
  - Match if `stored.friendly_name == candidate.friendly_name` AND `stored.device_type == candidate.device_type`.
  - This preserves user intention when a customized device is temporarily disabled or re-enabled with its custom name intact.

#### Rule C: Normalized Original-to-Original Matching
When a device is moved to another USB port or re-paired, Windows frequently **resets the friendly name back to the original default**. To match the original names across ports, the original name **must be normalized**:
- Windows PnP injects enumeration prefixes into `PKEY_DeviceInterface_FriendlyName` on re-plugging (e.g. `"Logitech Webcam C930e"` on Port 1 becomes `"2- Logitech Webcam C930e"` on Port 2, and `"3- ..."` on Port 3).
- **Normalization pipeline:**
  1. Strip leading prefixes: `^\d+\s*-\s*` (e.g. `"2- "`, `"3 - "`).
  2. Strip trailing clone counters: `\s*\(\d+\)$` (e.g. `" (1)"`, `" (2)"`).
  3. Canonical original name:
     $$\text{canonical\_original} = \text{clean}(DeviceDesc) + \text{ " (" } + \text{clean}(DeviceInterface) + \text{")"}$$
- **Original Name Match Invariants:**
  - `clean_original == clean_original`
  - `device_type` must match (`Input` vs `Output`)
  - `bus_type` must match (`USB` vs `BTHENUM` vs `HDAUDIO`)
  - `form_factor` must match (`Speakers` vs `Headphones` vs `Headset` vs `Microphone`)
  - **Strict Unambiguity:** If multiple active devices share the same cleaned original name (e.g. two generic `"Speakers (Realtek(R) Audio)"` or two `"Speakers (USB Audio Device)"`), **do not guess**—abort name-based migration.

### 3. Collision Prevention for Identical Non-Serial USB Peripherals
Budget USB audio cards, DACs, and microphones often do not burn unique serial numbers into firmware. If a user connects two identical microphones:
- Both share the same VID/PID and description.
- Blind VID/PID migration would clobber or swap volume settings.

**Rule:**
- Automatic migration on VID/PID alone is **only permitted when there is an unambiguous 1-to-1 match** (exactly one missing device matches exactly one newly arrived active device).
- If multiple candidates exist, fall back to USB physical port topology (`DEVPKEY_Device_LocationPaths`, e.g., `PCIROOT(0)#...#USB(1)#USB(2)`).

## 5. Comprehensive Matching Architecture

The migration process runs whenever endpoint changes occur, comparing **Missing Registered Devices** against **Unclaimed Active Devices**:

```text
                     [ Missing Registered Device (Old ID) ]
                                        │
           ┌────────────────────────────┴────────────────────────────┐
           ▼                                                         ▼
 Query GetDevice(old_id)                                  Read Saved Fingerprint
 OpenPropertyStore(STGM_READ)                             from PersistentState
 (Recovers disconnected PKEYs)                            (Offline fallback)
           │                                                         │
           └────────────────────────────┬────────────────────────────┘
                                        ▼
                             [ Hardware Fingerprint ]
                                        │
    ┌───────────────────────────────────┼───────────────────────────────────┐
    ▼                                   ▼                                   ▼
[ Hardware ID Matching ]       [ Name Matching Engine ]       [ Fallback VID/PID ]
(MAC / USB Serial Number)      (Strict Anti-Cross-Match)      (Unambiguous 1:1)
    │                                   │                                   │
1. Bluetooth MAC               1. Both Custom:                Single unclaimed
   + FormFactor (A2DP vs HFP)     friendly == friendly        VID/PID candidate
2. USB Serial Number           2. Cleaned Original:           + FormFactor
   + VID/PID + FormFactor         clean_orig == clean_orig    + DeviceType
                                  + BusType + FormFactor
                                  (Strict 1:1 match)
```

### Confidence Tiers

| Tier | Strategy | Required Criteria | Confidence |
|---|---|---|---|
| **Tier 1** | **Exact Hardware ID** | Bluetooth MAC (BD_ADDR) OR unique USB Serial Number + `DeviceType` + `FormFactor` | **100%** |
| **Tier 2** | **Hardware Profile & Interface** | USB `VID/PID` + Sub-interface (`MI_xx`) + `DeviceDesc` + `FormFactor` (Unambiguous 1:1) | **90%** |
| **Tier 3** | **Internal Hardware Profile** | `HDAUDIO` Vendor/Subsystem ID + Monitor Name / Jack Type + `FormFactor` | **85%** |
| **Tier 4** | **Custom-to-Custom Name** | `is_custom && is_custom` + exact custom `friendly_name` match + `DeviceType` | **80%** |
| **Tier 5** | **Normalized Original Name** | `clean_original == clean_original` + `BusType` + `FormFactor` + `DeviceType` (Unambiguous 1:1) | **75%** |
| **Tier 6** | **Heuristic VID/PID Fallback** | Unclaimed `VID/PID` + `FormFactor` match (Strictly 1 missing to 1 active pair) | **60%** |

## 6. Proposed Data Structures & Schema Changes

### `src/types.rs`

```rust
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize, Clone, Copy, PartialEq, Eq, Hash)]
pub enum DeviceBusType {
    Usb,
    Bluetooth,
    HdAudio,
    RootVirtual,
    Unknown,
}

#[derive(Debug, Serialize, Deserialize, Clone, PartialEq, Eq, Default)]
pub struct DeviceFingerprint {
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub bus_type: Option<DeviceBusType>,

    /// Raw driver description from PKEY_Device_DeviceDesc (e.g. "Speakers", "LU28R55")
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub hardware_desc: Option<String>,

    /// Audio adapter product name from PKEY_DeviceInterface_FriendlyName
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub interface_name: Option<String>,

    /// Canonical cleaned original name: "{clean(desc)} ({clean(interface)})"
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub clean_original_name: Option<String>,

    /// True if PKEY_Device_FriendlyName differed from default template at registration
    #[serde(default)]
    pub is_custom_name: bool,

    /// Bluetooth 48-bit MAC address (12 hex digits)
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub mac_address: Option<String>,

    /// USB Vendor ID and Product ID
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub usb_vid_pid: Option<(u16, u16)>,

    /// USB Serial Number (only if not a synthetic port hash)
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub usb_serial: Option<String>,

    /// Composite interface index (e.g. MI_00, MI_01)
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub interface_index: Option<u8>,

    /// Physical device container GUID
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub container_id: Option<String>,

    /// Audio endpoint form factor (e.g. 1=Speakers, 2=Headphones, 3=Headset, 4=Microphone)
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub form_factor: Option<u32>,
}

#[derive(Debug, Serialize, Deserialize, Clone)]
pub struct DeviceSettings {
    #[serde(flatten)]
    pub volume_lock: VolumeLockPolicy,
    #[serde(flatten)]
    pub unmute_lock: UnmuteLockPolicy,
    pub device_type: DeviceType,
    pub name: String,

    /// Hardware fingerprint for robust ID migration across ports and re-pairing
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub fingerprint: Option<DeviceFingerprint>,
}
```

### Backward Compatibility
Because all new fields in `DeviceFingerprint` and `fingerprint: Option<DeviceFingerprint>` use `#[serde(default, skip_serializing_if = "Option::is_none")]`, existing configuration files load without error or migration step.

## 8. Implementation Roadmap

### Phase 1: Property Store Query Support
- Update Windows FFI bindings in `src/bindings.rs` to include the required property keys (`PKEY_Device_DeviceDesc`, `PKEY_DeviceInterface_FriendlyName`, `PKEY_Device_EnumeratorName`, `PKEY_Device_ContainerId`, `PKEY_AudioEndpoint_FormFactor`, and `{b3f8fa53...}`).
- Add a helper in `src/audio/windows.rs` to extract a complete `DeviceFingerprint` from any `IMMDevice`.

### Phase 2: Parsers & Canonical Normalization
- Implement regex parsers for the PnP interface string:
  - Extract Bluetooth MAC address (`&<12-hex-mac>_`).
  - Extract USB VID/PID (`VID_[0-9A-Fa-f]{4}&PID_[0-9A-Fa-f]{4}`).
  - Extract USB Mutual Interface (`MI_[0-9A-Fa-f]{2}`).
  - Detect serial numbers vs port topology hashes (presence of `&` separator).
- Implement name canonicalization & detection:
  - Detect `is_custom_name`: `friendly_name != format!("{desc} ({interface})")`.
  - Canonical original name generator stripping `^\d+\s*-\s*` and `\s*\(\d+\)$`.

### Phase 3: Migration Cascade Engine
- Refactor `src/audio/migration.rs`:
  - When a device ID is missing, attempt on-the-fly recovery via `backend.device_fingerprint(&old_device_id)` (calling `GetDevice` without `Activate`).
  - Fall back to the saved `fingerprint` from `DeviceSettings`.
  - Evaluate unclaimed active devices against missing devices through Tiers 1–6.
  - Enforce the Anti-Cross-Matching principle (no custom $\leftrightarrow$ original name matching).
  - Apply multi-endpoint constraints (`DeviceType` and `FormFactor`).

### Phase 4: Validation & Logging
- Unit tests covering:
  - Bluetooth re-pairing migrations with identical MAC but different endpoint IDs.
  - Multi-endpoint headsets (ensuring Game output does not migrate to Chat output).
  - USB port relocation migrations.
  - Custom user-renamed device migrations with Windows name resets.
  - Rejection of cross-category name matching (preventing custom name matching default original name).
  - Collision rejection when multiple identical non-serial USB devices are present.
- Informative `log::info!` logging specifying the exact match tier and rationale during migrations.

## 9. Event-Driven Triggers & Debounced Execution Architecture

To guarantee that device migration and volume lock enforcement execute automatically in the background—without requiring application restarts or user interaction with the tray icon—Volume Locker responds to all of the following events:

1. **`IMMNotificationClient` Events (Full Surface Area)**:
   - `OnDeviceAdded`: Fires when an endpoint is added to the system (e.g. plugged into a new port or newly paired).
   - `OnDeviceStateChanged`: Fires when a device transitions between `ACTIVE`, `DISABLED`, `NOTPRESENT`, and `UNPLUGGED`.
   - `OnDeviceRemoved`: Fires when an endpoint is uninstalled.
   - `OnDefaultDeviceChanged`: Fires when the system default audio endpoint changes.
   - `OnPropertyValueChanged`: Fires when an endpoint's property store is updated (e.g. user renames a device in Windows Sound Settings, or driver completes writing properties on plug-in).

2. **200ms Settling Debounce**:
   - When a USB or Bluetooth device arrives, Windows fires a rapid burst of notifications (`OnDeviceAdded`, several `OnPropertyValueChanged`, and `OnDeviceStateChanged`).
   - A dedicated worker thread coalesces burst notifications using a 200ms quiet-window debounce, ensuring migration runs only once after driver initialization and property writes are fully complete.

3. **System Power Resume (`RegisterSuspendResumeNotification`)**:
   - Listens specifically for system resume events (`PBT_APMRESUMEAUTOMATIC` and `PBT_APMRESUMESUSPEND`) when waking from sleep or Modern Standby (ignoring suspend since the machine is entering sleep).
   - Dispatches a settled device check 500ms after wake to allow USB hubs and Bluetooth adapters to power up and re-establish links.
   - Synchronously re-verifies and enforces volume locks and unmute locks across all locked devices upon wake, guarding against driver volume resets during system sleep.
